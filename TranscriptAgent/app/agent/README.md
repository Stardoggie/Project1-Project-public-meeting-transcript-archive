This is a project generated by the AgentCore CLI!

# Layout

The generated application code lives at the agent root directory. At the root, there is a `.gitignore` file, an
`agentcore/` folder which represents the configurations and state associated with this project. Other `agentcore`
commands like `deploy`, `dev`, and `invoke` rely on the configuration stored here.

## Agent Root

The main entrypoint to your app is defined in `main.py`. Using the AgentCore SDK `@app.entrypoint` decorator, this
file defines a Starlette ASGI app that runs a LangGraph graph.

- `graph/graph.py` wires the graph: `agent` → `tools` → `agent`, with destructive tool calls routed to `confirm`.
- `graph/nodes.py` holds the nodes, the system prompt and the rules for which tool calls need the user's confirmation.
- `transcript_tools.py` defines the archive tools; `model/load.py` instantiates the Bedrock model.

Conversation state is checkpointed per session: AgentCore Memory when deployed (`MEMORY_AGENTMEMORY_ID`), in-process
memory locally. The agent only remembers within a session; the archive itself is the long-term record, so the memory
in `agentcore/agentcore.json` has no long-term strategies.

## Payload

The Runtime accepts a JSON object. `parse_payload()` reads:

- `prompt` (string) — the user's message. The conversation history is kept per session, so send only the new message.
- `confirm` (boolean, optional) — answers a pending confirmation without a prompt. `true` runs the action; anything else cancels it.
- `actorId` (string, optional) — identifies the end user in the session's checkpoints. Defaults to `"default"`.

The `session_id` is not in the body — it comes from the `X-Amzn-Bedrock-AgentCore-Runtime-Session-Id` header (`context.session_id`); reuse it to continue a conversation. A request without the header gets a fresh session id
of its own, so header-less callers never share a conversation or answer each other's confirmations; a pending
confirmation can only be answered with the header.

```json
{ "prompt": "Delete meeting 12", "actorId": "user-123" }
```

## Confirmations

Deleting a governing body or meeting, or replacing the audio of a meeting that already has a transcript, pauses the
graph. The response ends with a `confirmation_required` event describing exactly what will happen. The next request in
the same session answers it: only a plain "yes" (any case, trailing `.` or `!` allowed) or `"confirm": true` runs the
action. Anything else, including "y", "ok", "sure" or "yes please", cancels it; a reply other than a plain no is then
handled as a new message. A delete of an id that doesn't exist isn't confirmed at all: the tool reports it not found. If the lookup fails, the app
still asks. The delete tools the model calls never delete anything themselves; only a yes to the app's own prompt
runs the delete, so a model can't authorise one, whatever it passes or the user says in chat.

## Response events

Each streamed event is a JSON object with `node` (`agent`, `tools` or `confirm`), `type` (`ai`, `tool` or
`confirmation_required`) and `text`; `ai` events that call tools add `tool_calls`, and `tool` events add `tool`.
`ai` text is the agent's full reply; `tool` text is only the first 2,000 characters of what a tool returned.

When the user asks to see a full transcript, the `show_full_transcript` tool sends it straight to the caller as a
`transcript` event (`meeting_id`, `title`, `meeting_date`, `transcript`). The model only gets a short note that it was
shown, so it never reads or retypes the text.

## Environment Variables

| Variable | Required | Description |
| --- | --- | --- |
| `DATABASE_SECRET_ID` | One of these two | Name of the Secrets Manager secret with the database's host, port, username, password and dbname; read at startup (the deployed agent uses this) |
| `DATABASE_URL` | One of these two | Postgres URL of the archive database; when set it is used instead of the secret |
| `AWS_REGION` | Yes | Region for Transcribe, Comprehend, S3, Secrets Manager and AgentCore Memory |
| `MEETING_BUCKET_NAME` | Yes | S3 bucket for recordings and Transcribe output |
| `MEMORY_AGENTMEMORY_ID` | No | AgentCore Memory id (set by `agentcore deploy`). Unset: in-process checkpoints |
| `MEETING_LOG_LEVEL` | No | Log level of the archive code's logs (default `DEBUG`) |
| `DATABASE_TEST_URL` | Tests only | A separate database for the tests; they refuse to use `DATABASE_URL`'s |

# Developing locally

If installation was successful, a virtual environment is already created with dependencies installed.

Activate the environment with `source .venv/bin/activate` on macOS/Linux, `.venv\Scripts\activate.bat` in Windows
Command Prompt, or `.\.venv\Scripts\activate.ps1` in Windows PowerShell.

`agentcore dev` will start a local server on 0.0.0.0:8080.

# Deployment

After providing credentials, `agentcore deploy` will deploy your project into Amazon Bedrock AgentCore.

The deployed runtime is set up entirely in `agentcore/agentcore.json`; there is no CDK stack code:

- `envVars` gives the runtime `DATABASE_SECRET_ID` (the secret's name, never the password), `MEETING_BUCKET_NAME` and
  `AWS_REGION`. AgentCore adds `MEMORY_AGENTMEMORY_ID` itself.
- `additionalPolicies` attaches the existing IAM managed policy `meeting-transcript-archive` (S3 audio and transcripts,
  Transcribe, Comprehend, and reading the database secret). `iam/policy.json` at the repo root is a copy of it.

Both the secret and the policy are made outside this project (in the AWS console) and must exist before deploying.
The database's security group must allow port 5432 from the runtime, which has no fixed address.

Invoke the deployed Runtime with its native payload (session ids need at least 33 characters):

```bash
agentcore invoke --runtime agent --payload '{"prompt":"Hello!"}' --session-id <33+ characters>
```

or chat with it from `../../cli/` with `chat.py --deployed` (see that README).
